# Edge Submission Protocol

How an *edge* host submits work to a *hub* over an object store, without any
inbound network access to the hub.

This document is the normative reference for two implementations: weft, and
agent-review. The envelope, the keyring, and the verification order are one
shape with two callers. Anything a caller adds belongs in its own payload,
never in the envelope.

Related:

- [Federated R2 Blackboard](federated-blackboard.md) — a *different* protocol;
  see [Relationship to the blackboard](#relationship-to-the-blackboard)
- [0017](../decisions/0017-use-host-addressed-r2-mailboxes-for-isolated-inventory-hosts.md)
  — host-addressed mailboxes, the same delivery shape in the opposite direction

## Roles

**Hub** — holds the authoritative database, owns queue, placement, and
artifacts. It is the only party that decides anything. It *pulls*.

**Edge** — a host that may submit work. It holds no database, makes no
placement decision, and reaches the hub through exactly one channel: writing
objects to the inbound store. It never connects to the hub.

The asymmetry is the security property. An edge that is fully compromised can
write objects. It cannot open a connection to the hub, cannot read the hub's
database, and cannot cause the hub to do anything the hub did not already
decide it would do on its behalf.

## Store layout

Inbound submissions live in a store **separate from the results store**, with
credentials that grant no access to results.

```text
edge/v1/payload/<payload-digest>     content-addressed payload blobs
edge/v1/source/<source-digest>       content-addressed working-tree closures
edge/v1/inbox/<nonce>                the pointer; a framed, signed envelope
edge/v1/ack/<nonce>.json             hub-written acknowledgement
```

There is deliberately **no key material in this store**, in either direction.
See [Nothing in the store is authority](#nothing-in-the-store-is-authority).

`<nonce>` is a ULID generated by the edge. It is the object key, the replay
identifier, and the idempotency key — one value doing all three jobs, so a
retried submission cannot become a second job by construction.

### Nothing in the store is authority

**A fact stored where an untrusted party can write it must never be read back as
authority.**

The inbound bucket is writable by every edge. Two things follow, and they are
the same rule applied twice:

- **Verification keys are never read from the store.** The hub's keyring is
  local and authoritative. Were the hub to load keys from the bucket, write
  access would become key-registration access: an attacker would register a key
  and sign whatever it liked, every other check would still run, and
  authentication would silently become a formality. That is worse than having
  no signatures at all, because the refusal messages would then assert an
  identity nobody verified.
- **Acknowledgements confer nothing.** They are hub-written status the edge
  reads for progress, and an edge that believed a forged ack would learn a
  wrong status, not gain a capability.

Naming the rule once is the point. Both cases above look locally reasonable, and
the third instance of it will too.

## Publish order

The order is load-bearing. An interrupted submission must never leave a
pointer to a payload that is not fully present.

1. Write the working-tree closure to `edge/v1/source/<digest>` when the
   submission names one. It is a separate content-addressed object because a
   source closure can be much larger than the job request.
2. Write the payload to `edge/v1/payload/<digest>`. Content-addressed, so a
   partial or repeated write is harmless and a retry is free.
3. Write the pointer to `edge/v1/inbox/<nonce>` with `If-None-Match: *`.

Step 3 is the commit point. The conditional write makes it atomic: the first
writer wins and a retry of an already-committed submission fails the
precondition, which the edge reports as *already submitted*, not as an error.

The hub polls `edge/v1/inbox/`, and for each pointer it has not yet processed,
runs [verification](#verification-order) and then admission. A failure for one
pointer does not stop the pass; the hub continues through the listed keys and
reports their errors together.

The seen-set is the durable admission boundary. If a job submission is recorded
there but has no job row, recovery removes that nonce so the next pass can
re-admit it through the idempotent record path. The other registered kinds do
not create job rows. A recorded job control, bug report, or plan-ended payload
therefore receives a generic accepted acknowledgement and its pointer drains.
Recovery authenticates the stored envelope again, but does not repeat freshness
or replay checks whose successful result is already recorded.

## Frame

The object at `edge/v1/inbox/<nonce>` is a line-framed envelope:

```text
weft-edge/1\n
<key-id>\n
<base64 detached signature>\n
<envelope octets, verbatim to end of object>
```

The signature covers **exactly the envelope octets** — everything after the
third newline, byte for byte.

There is deliberately no canonical serialization step. The envelope is
serialized once, by the edge, and the signature covers those octets forever
after. The hub never re-serializes the envelope to check a signature, so the
entire class of canonicalization bugs — key ordering, whitespace, number
formatting, Unicode normalization — cannot arise.

`<key-id>` sits outside the signature because it selects the key used to check
the signature. It is an unauthenticated hint. Naming a different key makes
verification fail; it cannot make verification succeed.

Line 1 is the **frame** marker and guards the framing. `protocol_version`
inside the envelope guards the **schema**. They fail differently and at
different times; see [Verification order](#verification-order).

## Envelope

```json
{
  "protocol_version": 1,
  "payload_kind": "weft.job-submission/v1",
  "submitter_host": "studio",
  "deployment_source_digest": "sha256:...",
  "nonce": "01JBQ...",
  "submitted_at": "2026-09-04T02:29:51.915Z",
  "payload_digest": "sha256:..."
}
```

An empty `target_constraints.hosts` means the hub chooses from its configured
allowlist. The admitted target set is stored on the job, the job remains
unplaced, and ordinary placement applies the job's GPU, input, and other
constraints within that set. The target set is a hard eligibility filter for
every later placement attempt, including automatic moves and direct dashboard
launches. Each placement path evaluates the authorization stored on its job
rows. An acknowledgement for this case has phase `placement_pending`; `placed`
requires a concrete host.

| Field | Meaning |
| --- | --- |
| `protocol_version` | Envelope schema version. Unknown values are quarantined, never parsed leniently. |
| `payload_kind` | Which payload schema this carries. The hub routes to a validator by this value rather than inferring one. |
| `submitter_host` | The submitting host. Must equal the host bound to the verifying key; see [Host binding](#host-binding). |
| `deployment_source_digest` | Which build of the edge produced this. Provenance for "what code decided to submit this". |
| `nonce` | ULID. Object key, replay identifier, idempotency key. |
| `submitted_at` | RFC3339Nano. Bounds replay validity against the kind's TTL. |
| `payload_digest` | Binds the pointer to the payload. Verified before the payload is used. |

The envelope carries **only delivery and provenance**. It has no authority
fields at all.

### Authority lives in the payload

Anything that grants or bounds permission — an execution target, a spend
ceiling — belongs to the payload of the kind that has such a concept, not to
the shared envelope.

This costs nothing in integrity. `payload_digest` is inside the signature, so
altering a payload invalidates the pointer that names it: a party who can write
the inbound store but cannot sign still cannot raise a ceiling or redirect
execution. What it buys is that a caller with no notion of spend or placement
never carries authority fields it must set to null, and a hub can never read
authority out of an envelope whose kind has none.

For `weft.job-submission/v1` the payload is:

```json
{
  "command": "uv run train.py",
  "working_dir": "...",
  "project": "...",
  "source_digest": "sha256:...",
  "spend_ceiling_usd": 5.0,
  "target_constraints": { "hosts": ["studio"], "gpu": "nvidia>=24GB" }
}
```

### Per-kind policy

Two things are configured per kind rather than fixed protocol-wide, because
they mean different things to different callers:

- **Time-to-live.** A job submission admitted six hours late may be unwanted
  work; a record that states a fact is still true six hours later. An unset TTL
  means "use the hub default", not "never expire" — a kind that should genuinely
  never expire declares it explicitly, so a forgotten value fails toward a bound
  rather than toward none. Exemption exists for kinds whose payload states a
  fact: dropping such a record would be read downstream as the event never
  having happened, a silent absence standing in for a negative observation.
- **Content idempotency.** For a kind whose payload *is* its identity, two
  submissions with the same payload are one submission and the hub dedupes on
  `(signing key, payload_kind, payload_digest)` as well as on the nonce. The
  signing key is part of that tuple because a kind's effect can be per-signer:
  two different keys sending identical bytes are two different effects. This is **false**
  for job submissions: running the same command twice is a legitimate request,
  so two nonces must mean two jobs.

A kind absent from the hub's registry is refused, never admitted under a
default, so accepting a new caller is a deliberate act on the hub.

The weft hub registers these kinds:

| Kind | TTL | Content-idempotent | Identity and rationale |
| --- | --- | --- | --- |
| `weft.job-submission/v1` | 1 hour | No | Repeating the same command can deliberately create another job. The delivery nonce identifies each submission. |
| `weft.job-control/v1` | 15 minutes | Yes | A control request concerns work in flight, so an old instruction is unsafe to apply after the job's context may have changed. `request_id` identifies one instruction: an exact retry collapses, while two deliberate requests remain distinct even when they name the same job and action. |
| `weft.bug-report/v1` | Never expires | Yes | A report or note states a fact that does not become false in transit. Its `report_id` identifies that fact, so equal report fields from separate observations do not collapse. |
| `weft.plan-ended/v1` | 24 hours | Yes | Ending an already-ended plan is harmless. The generous bound lets delayed termination close authority without making every termination record permanent. |

Job control is plan-scoped by default. The hub reads the signing key id from
the target job's durable provenance and requires it to equal the key that
signed the verified control envelope. A confirmed missing job or a different
key is refused with `job_control_authority`; an unreadable provenance lookup is
unknown and remains pending. Hub configuration may set
`allow_foreign_job_control = true` to widen this authority deliberately.
Restart and edit also pass through the spend-ceiling authorization used for a
job submission. A control that names no ceiling preserves an existing ceiling
below the plan grant and clamps an absent or higher ceiling to that grant. An
edit that names `--max-spend` installs the admitted requested ceiling. On an
edge, `edit --max-spend 0` requests the full plan grant; it never clears the
job's enforced ceiling. The hub commits any required ceiling reduction before
the job becomes dispatchable. A confirmed decision that the requested action
is invalid for the current job or bug state is acknowledged as `action_failed`
and drains. A database, locking, or I/O failure leaves the result unknown and
the pointer pending for a later pass.

## Verification order

Strictly ordered. Each step runs only if every previous step passed.

1. **Frame** — line 1 equals `weft-edge/1`. Otherwise refuse: *unframed*.
2. **Key lookup** — `<key-id>` resolves in the keyring. Otherwise refuse:
   *unknown key*.
3. **Signature** — Ed25519 verify over the envelope octets. Otherwise refuse:
   *bad signature*. **The envelope has not been parsed at this point.**
4. **Parse** — only now decode the octets as JSON.
5. **Version** — `protocol_version` is one this hub implements. Otherwise
   quarantine: *unknown protocol version*. The object is retained, not deleted.
6. **Kind** — `payload_kind` is registered on this hub. Otherwise quarantine:
   *unknown payload kind*.
7. **Host binding** — `submitter_host` equals the verifying key's bound host.
   Otherwise refuse: *submitter host mismatch*.
8. **Key validity** — `submitted_at` falls within the key's window, and the key
   is not revoked. Otherwise refuse: *key not yet valid*, *key expired*, or
   *key revoked*.
9. **Freshness** — within the kind's TTL, not implausibly future-dated.
   Otherwise refuse: *expired* or *future dated*.
10. **Replay** — `nonce` is not in the seen-set. Otherwise refuse: *replayed
    nonce*. Recorded before admission, so a crash between check and admission
    cannot admit twice.

Then, and only then, the payload is fetched, checked against `payload_digest`,
parsed under its declared kind, and authorized.

Steps 1 through 3 are authentication. The boundary between 3 and 4 is the one
that matters most: **nothing derived from unverified bytes influences any
decision, including the decision of how to parse them.** Step 5 in particular
must not run before step 3, or an unauthenticated field would steer the hub's
handling.

### Host binding

The keyring binds a key to a host, and the envelope also states one. Without an
equality check between them, a valid key for one host could sign an envelope
naming another, and the hub would record provenance that is false while every
other check passed.

That is worse than recording no provenance at all, because it reads as
verified. Provenance on a job row is a fact the hub asserts about work it did
not observe; the only thing making it a fact is this check.

## Authorization is separate from authentication

A valid signature proves *who wrote this*. It never proves *this may run*.

Every authorization check runs on the verified envelope, and a valid signature
never causes one to be skipped:

- **Payload digest.** The fetched payload must hash to `payload_digest`. This
  runs first, because the two checks below read fields from the payload and are
  meaningless until it is known to be the payload that was signed.
- **Execution target allowlist.** The payload's `target_constraints` is checked
  against the hub's configured allowlist. The allowlist is hub-side
  configuration; no submission can extend it. It can never include the hub's
  own host, which is enforced when the policy is constructed rather than per
  submission, so a misconfiguration fails at startup rather than on the first
  submission that exploits it. An empty host request authorizes the whole
  allowlist without selecting one member. The admitted set is persisted on the
  job and remains a hard placement constraint.
- **Spend ceiling.** The payload's `spend_ceiling_usd` is checked against the
  hub's configured maximum.

A ceiling above the hub's maximum is **refused, not clamped**. Clamping would
run the work under a ceiling its submitter did not choose, which is the same
error class as best-effort parsing: proceeding on a guess about intent. An edge
that does not know the hub's configuration should send no ceiling and receive
the hub's; an edge that names one is making a specific claim, worth honoring or
refusing but not silently rewriting.

This is the sharpest instance of the general rule, because an autonomous
session with no human watching can spend real money on rentals. Signing makes a
raised ceiling attributable. Only hub configuration makes it legal.

This separation is deliberate and is recorded as a decision, because the
natural simplification — "the constraints are inside the signature, so trust
them" — removes the property the design exists to provide. A signed envelope
from a compromised edge carries an attacker's constraints with a perfectly
valid signature.

Refusal messages must name which of the two failed. "Signature valid; target
`hub-laptop` is not an allowed execution target" tells an operator what to fix.
"Rejected" does not.

## Keyring

The hub holds public keys. One key per **plan execution**, minted when a plan is
handed to a host.

```json
{
  "key_id": "studio-plan-42",
  "host": "studio",
  "plan_id": "plan-42",
  "project": "lm2",
  "public_key": "base64...",
  "not_before": "2026-09-04T00:00:00Z",
  "not_after": "2026-09-04T06:00:00Z",
  "spend_ceiling_usd": 5.0,
  "revoked_at": null
}
```

### Authority is a lease, not a grant

`not_after` is short and slides forward while the hub can verify that the key's
project remains under settled remote ownership on the key's host. Renewal is
hub-side: the edge cannot assert its own liveness or extend its authority.

The daemon reads `research-site status --json`, requires schema
`research-site.status/v1`, and joins rows to keys by exact project name. It
renews only an unrevoked, unexpired key whose unique project row has
`owned_by: "remote"`, `settled: true`, and a `remote_host` matching the key's
host. A missing, duplicate, malformed, unsettled, local, or mismatched row does
not renew the key. Source errors leave ownership unknown and do not become
evidence that the project is local.

Renewal is conditioned at project granularity because that is the liveness
state the hub can observe. It cannot see an individual plan's coordination
lease on the edge. A returned tree therefore stops renewal, but an abandoned
plan on a still-owned project keeps renewing until the project returns.

The default is a six-hour window checked hourly. This tolerates several missed
checks while making expiry, rather than an open-ended credential, the outcome
when ownership evidence disappears. A window that has lapsed is never reopened:
doing so would retroactively admit every submission signed during the gap. The
manual `weft edge key renew` command follows the same rule.

**Window length has a floor set by clock skew, not by security.** Verification
refuses future-dated submissions and bounds staleness by TTL, so a few minutes
of drift between hosts is harmless at hour scale and produces a refusal storm
at minute scale. The floor is one hour. The renewal interval must be shorter
than the window so one delayed check does not lapse a live plan.

### Ending a plan

A plan's grant is bounded by two events, and both of them happen on the edge
while the keyring lives on the hub. Mint is deliberately hub-side — granting
money must not be self-service — but ending needs a path back, or a finished
plan's budget stays spendable until the whole project returns.

Three paths close a grant, whichever comes first:

1. **Explicit hub-side end.** The operator knows the plan finished and sets
   `not_after` to now.
2. **Edge-signalled end.** The edge submits a `weft.plan-ended/v1` payload
   through the ordinary inbound path. This is the normal path when a plan
   reaches terminal disposition.
3. **Lease expiry.** Renewal stops because ownership is no longer settled and
   remote, or because the hub cannot verify it before the window ends.

Path 2 does not weaken the rule that an edge must never assert its own
liveness. That rule exists because a compromised edge extending its own window
defeats the lease; a compromised edge *ending* its own plan defeats nothing.
The general form, which the optional downward-only spend request also uses:
**a request that can only reduce authority needs no trust.**

Two constraints make it safe rather than a denial-of-service surface. The
request must be signed like any other submission, and it may end only **its
own** plan — the plan id in the payload must match the one bound to the
verifying key. The worst case is then that whoever already holds a plan's key
can end that plan, which is either the plan itself or a host compromise with
better options available.

### Ending versus repudiating

Two outcomes with different subjects, from one field and one flag:

| Action | Mechanism | Meaning |
| --- | --- | --- |
| Plan ends normally | stop renewing, or set `not_after` to now | Bounds **admission**. Nothing new is accepted; everything already admitted stands and stays verifiable. |
| Key believed compromised | set `revoked_at` | Repudiates **evidence**. Past signatures stop proving anything. |

The first works only because key validity is judged against the envelope's
`submitted_at` rather than the hub's clock at processing time. Moving
`not_after` backwards therefore refuses new submissions without invalidating
past ones — which is exactly the distinction, with no second field.

Using revocation to end a plan routinely would retroactively repudiate every
submission it legitimately made. That is worse for a caller whose records are
long-lived evidence than for one whose submissions are transient work.

**A lapse must say so.** When a window closes mid-plan the edge cannot
distinguish that from any other refusal, and an autonomous submitter reading a
generic rejection will retry forever. The refusal names the lapse and states
that the submission itself was fine.

**Keyring rows are append-only.** A window that closed months ago is not a
reason to delete a row: a record signed inside it must remain verifiable, or it
degrades from evidence to assertion. Pruning the keyring for tidiness is exactly
the good-faith cleanup that would cause this.

### Key material

Keypairs are generated **on the edge**. The hub pulls only the public half, over
SSH it initiates, against the host's agent account. No private key is ever in
transit or at rest anywhere but the host that uses it, and the per-plan
lifecycle needs no secret-delivery channel.

The pull is one command, and the key travels on stdout rather than as a file:

```console
$ ssh agent@studio 'weft edge key mint --plan <plan-id>'
<base64 public key>
```

`weft edge key mint` generates the keypair if the plan has none, stores the
private half mode 0600 outside any synced tree, and prints **only** the public
half. It refuses to run on a hub, and it is **idempotent per plan**: if a
keypair for that plan exists, it prints the existing public key rather than
replacing it, and refuses outright if the stored key belongs to a different
plan.

The key id is `<host>-<plan>`, derived independently on both sides, so mint and
registration agree without transmitting it. That only holds while keys are
stored per plan, which is why the edge's key directory is keyed by plan and why
an edge validates its loaded key against its configured plan before signing. Without that, a retried ship would orphan the key the hub already
registered and the edge would sign with one the hub has never seen — surfacing
as a bad-signature refusal whose message points nowhere near the cause.

This round trip happens exactly **once per plan**. Renewal is hub-local, so
there is no recurring channel to the edge.

**The SSH host key is the root of trust for edge identity.** A public key needs
integrity, not confidentiality, and host-key verification is exactly that. The
signature chain terminates in the hub's knowledge of the edge's host key, not
in the object store. If the host key is unknown or has changed, the pull fails
and the mint fails with it, which is the correct outcome rather than an
obstacle to work around.

A private key must **never** be written inside the project tree. That tree is
version-controlled and travels back to the hub, so a key placed in it lands in
history on both machines — and sync excludes do not help, because a tracked file
is not excluded.

## Limits, stated honestly

The signing key sits on the edge, next to that edge's credentials for the
inbound store. Anyone who can read one can read the other.

This raises the bar from **leaked bucket credential** to **host compromise**,
and no further. It does not protect against a compromised edge: such an
attacker signs whatever it likes with a valid key, and the hub's allowlist,
spend grant, and payload verification are what remain. That is exactly why
those are enforced independently of the signature.

**Grants close at different speeds.** A plan that ends cleanly closes its grant
immediately, by signalling. A plan whose project returns home stops renewing
and closes within one window. A crashed plan on a project that remains remotely
owned keeps its grant until the project returns; project ownership is the
finest liveness fact available to the hub.

**Nothing caps a plan's total spend.** The ceiling is enforced per submission
with no cumulative accounting, so a plan holding a live key can spend up to its
ceiling as many times as it submits. The ceiling bounds the blast radius of any
one submission, not the plan.

**Renewal makes hub availability a liveness dependency.** If the hub daemon
cannot obtain valid ownership evidence for one window, a live plan's key
lapses. The design accepts that cost because the edge use case is hub compute
saturation, not a sleeping hub.

**A sliding window does not bound one-time key exfiltration.** A copied key
works while the hub keeps renewing the original. Rotating the keypair each
window would narrow that exposure, at the cost of a recurring authenticated
key pull, and remains a hardening option rather than part of this protocol.

It is not a PKI. There is no certificate chain, no delegation, and no
revocation distribution beyond the hub's own keyring.

One algorithm, Ed25519, with no algorithm field anywhere in the frame or
envelope. Algorithm agility is a documented source of downgrade and confusion
vulnerabilities and buys nothing here, where both ends ship from one source
tree. A future change of algorithm is a `protocol_version` bump.

Not signed, deliberately: heartbeats, log lines, status reads, acknowledgements.
None carries authority, and signing them would enlarge the key-handling surface
while protecting nothing.

## Operational notes

These are requirements on how an edge is deployed, not on the protocol. They
are here because "no human in the loop" is only true if the surrounding host is
configured so that no human *can* be in it.

**No prompting.** An edge session runs unattended. If a tool-approval prompt can
appear at the moment of submission, the submission stalls forever against a
terminal nobody is reading. The harness on an edge host must be configured so
that no prompt can occur on the submission path.

**No spooling.** The hub is awake by assumption — the reason work moves to an
edge is that the hub is CPU-saturated, not that it sleeps. An edge call may
block on hub availability and must fail loudly when the hub is unreachable.
There is deliberately no local queue that drains later: a spool would convert a
loud failure into a silent delay, and the waiting agent cannot tell those apart.

**Bootstrap runs as the agent account.** The hub's key pull targets the
dedicated agent account on the edge host. Targeting a personal account would
block an unattended run on a biometric prompt, and would violate the access
invariant besides.

### When an acknowledgement never arrives

The edge's only feedback channel is the ack object, and it cannot connect to
the hub to ask. So the edge cannot distinguish *hub has not acked yet* from
*ack lost, overwritten, or never written*. This is inherent to the pull-only
design, not a gap in it, and the protocol therefore defines what happens rather
than leaving it to be discovered by an agent that has waited fifteen hours.

**A missing acknowledgement is unknown, never failure.** The wait never reports
a submission as failed because no ack appeared; it reports that no ack has
appeared, with elapsed time.

**Two triggers fire independently**, and both are configured constants rather
than statistics:

- an **elapsed ceiling** for the whole submission, and
- a **phase-stall trigger** — no observed phase change for longer than its
  threshold, default six hours.

The stall trigger exists because the ceiling alone is too slow: a wedged
submission at hour seven looks identical to a healthy long one until the
ceiling expires on day two.

**The verdict line must flip.** Progress output carries an explicit normality
verdict, and past either trigger that verdict changes from *within expectation
— no action indicated* to an escalation. A confidently reassuring progress line
printed at hour fifteen is the specific failure this rule prevents; a wait that
cannot ever say "escalate" is worse than one that prints nothing.

## Relationship to the blackboard

The [federated blackboard](federated-blackboard.md) is a **pool**: the hub
publishes specs, many agents compete, `claim.json` is the per-job contention
boundary, and claims expire and are renewed.

Edge submission is a **channel**: one writer, one reader, no competition, no
claiming, and the object is immutable once written.

They share the object-store abstraction and nothing else. Decision 0017
already declined to build addressed delivery on the blackboard protocol, for
this reason; the same reasoning applies here, in the opposite direction.
Merging them would put a security boundary inside a namespace whose design
assumption is cooperative mutation, and would drag signature handling onto
heartbeats and events that have no authority to protect.

## Transports

The protocol is defined over an object store with three operations: get, list,
and conditional put. Two implementations:

- **R2** — production.
- **Filesystem** — a directory tree, for tests and offline development.

Signature verification is **enabled in both**. The filesystem transport uses
test keys rather than disabled crypto, so verify-then-parse and every refusal
path are exercised on every test run. A transport that skipped verification
would leave the ordering property untested precisely where it is cheapest to
break.
